# Part 1 · UX 审计报告

> 审计日期：2026-07-25
> 审计人：用户体验研究员（UX Researcher）
> 方法：**专家启发式评估（Nielsen 10 项）+ 认知走查**，作为用户实证研究的**基线**；真实用户测试方案见 §1.6 与 Part 2。

## 1.1 研究目标与方法论

### 1.1.1 研究问题（对齐"了解用户使用需求与习惯"）
- **RQ1**：用户（尤其新手服主）能否独立完成"本地单机 → 专用服"整包迁移，并理解"何时进游戏验证世界可玩"？
- **RQ2**：双页信息架构（本地存档=发现 / 数据迁移=执行）是否符合用户心智模型，还是造成困惑？
- **RQ3**：高风险操作（修复主机存档 / GUID 改写）在 UI 上的呈现，是否会把用户引入超出其理解的风险？
- **RQ4**：备份 / 恢复 / 扫描根持久化机制的可预测性如何？用户能否预期副作用？
- **RQ5**：新手引导（server_path 设置、停服要求）的接受度与痛点。

### 1.1.2 方法论框架（混合方法）
| 阶段 | 方法 | 作用 | 状态 |
|------|------|------|------|
| 0 | 专家启发式评估 + 认知走查 | 基线，确证级问题 | **本次已完成** |
| 1 | 定性：5–8 人半结构化访谈 + 可用性测试（think-aloud） | 挖掘需求/习惯、发现卡点 | 待执行 |
| 2 | 定量：SUS + SEQ + 任务指标（n≈15–20） | 可泛化的可用性评分 | 待执行 |
| 3 | 三角验证 + 亲和图 | 收敛洞见、排优先级 | 待执行 |

### 1.1.3 偏差缓解（科学性保障）
- 招募覆盖**新手（只玩单机）/ 老手（管多服）**两类，避免单一画像偏差。
- think-aloud 减少回忆偏差；行为数据（完成率/时长/错误数）+ 主观（SUS/SEQ）+ 访谈三角验证。
- 主持人保持中立，不暗示"应该怎么用"。
- 参与者知情同意、可随时退出（伦理）。

## 1.2 当前界面使用逻辑梳理

### 1.2.1 信息架构（单一入口落地评估）
设计文档（`palworld-migration-design.md` Part 1 §1.2）主张：**「本地存档」页是发现与管理的唯一入口；「数据迁移」页只读复用已保存的扫描根，不再有手动选目录按钮。**

实测代码与该主张**基本一致**：
- `SaveManagementView.vue` 承担发现（`onPickLocalDir` L350 / `onPickServerDir` L375 / 卡片点"迁移"→ `router.push('/migrate', {source, type:'local'})` L324）。
- `SaveMigrationView.vue` 的源下拉由 `localWorlds`（来自持久化 `local_save_roots`）填充，**无独立手动选目录按钮**——符合文档。
- 预选衔接：迁移页 `onMounted` → `onDiscover().then(applyPendingSource)`（L499-501），读 `route.query.source` 回填源（L485-497）。**衔接设计合理**。

✅ **源/目标选择设计经复核为正确（非缺陷）**：源下拉含全部存档（本地单机 + 专用服），目标下拉只列专用服世界。合法迁移仅两种——**本地单机 → 专用服**、**专用服 → 专用服**；本地单机之间不可互迁（无业务场景，后端亦会拒绝）。因此**目标恒为专用服世界是正确的领域逻辑**，并非 UI 漏洞。早前一度被误读为"源有本地、目标没有"的 bug；经与用户复核确认：这是设计本意，**不应改为"两个都有"**。唯一可优化项是加一句中性引导文案（如"目标必须是专用服世界——本功能把世界搬进服务器"），消除初见困惑即可，不构成缺陷。

### 1.2.2 核心任务流（整包迁移，7 步）
1. 打开「本地存档」→ 自动发现单机 + 专用服世界（L214）
2. （可选）手动选目录兜底（L350/L375）
3. 点世界卡 → 弹详情 → 点"迁移" → 跳迁移页并预选源（L324）
4. 在迁移页选目标世界（L56）
5. 勾选"删除 WorldOption.sav"（可选，L85）
6. 点「执行整包迁移」→ 二次确认（L453）→ `migrateWorld`（L457）
7. **用户自行**启服进游戏验证（文档 §1.5 步骤 7，但 UI 无此引导）

### 1.2.3 状态与边界
- 服务器运行中：迁移被后端拒绝；前端 `ensureStopped()`（L384）尝试停服，但**确认弹窗是静态文案**，不实时显示服务器当前状态。
- 备份根互斥：`onPickBackupDir`（L402）选备份根时**静默从 `local_save_roots` 移除该目录**（L409-411）——副作用未告知。

## 1.3 启发式审计发现（基于代码实证）

| # | 严重度 | 位置 | 违反启发式 | 证据 | 用户影响 |
|---|--------|------|-----------|------|---------|
| **A1** | 🔴 高 | `SaveMigrationView.vue` L97–128 | #2 系统与现实匹配 / #9 错误预防 | 设计文档 §1.7 明确"角色/公会迁移**不得在世界验证前触发**，属后续独立阶段"；但 UI 把「① 修复主机存档（P0 灵魂步骤）」排在整包迁移**之前**，并标为灵魂步骤 | 诱导用户在做完安全拷贝、**尚未验证世界可玩**前，就去执行 GUID 改写高风险操作；与"先验证世界、再讨论角色"原则直接矛盾 |
| **A2** | 🔴 高 | `SaveMigrationView.vue` L247–254 vs L103 | #5 防错 / 一致性 | `canFixHost` 要求 `sourceWorld && targetWorld` 都设置，但修复功能只用 `fixWorld`。按钮可用态与功能脱钩 | 用户只选了修复世界想执行，按钮却灰着——功能"看似锁死"，误以为有 bug |
| **A3** | 🟠 中 | `SaveMigrationView.vue` L43–62 与 L65–95 | #8 极简设计 | 两组源/目标选择器绑定同一 `sourceValue`/`targetWorld` v-model，几乎重复 | 页面出现两对长得一样的下拉，用户困惑"这俩有啥区别"，认知负担 |
| **A4** | 🟠 中 | L437 / L455 vs L32 banner | #2 术语匹配 | banner( L32)承诺"UID/实例 ID 等底层术语对用户隐藏"，但修复确认弹窗显示原始 `${oldGuid}`（L437）、迁移确认显示本地绝对路径（L455） | 用户面对一长串十六进制 GUID / 内部路径确认操作，看不懂在确认什么，焦虑上升 |
| **A5** | 🟠 中 | `SaveManagementView.vue` L402–414 | #9/#10 可恢复性/帮助 | 选备份根时静默 `local_save_roots.filter(remove)`（L409），无提示 | 用户先加 F:\1 为本地根、后又选 F:\1 为备份根 → 本地源悄悄消失，困惑"我的存档哪去了" |
| **A6** | 🟠 中 | `SaveMigrationView.vue` L401–404 | #8 闭环缺失 | 成功 toast 用 `round-trip` 术语，且**无"下一步：启服验证"引导** | 迁移完用户不知道该干嘛；`round-trip` 对普通人 opaque |
| **A7** | 🟡 低 | 两页顶部 4–5 个 banner 常驻 | #8 极简 | `SaveMigrationView` 顶部堆叠 serverPathMissing/autoDiscovered/saveRoot/warn/pendingLocal（L16–40） | 横幅疲劳，关键信息被稀释 |
| **A8** | 🟡 低 | `SaveManagementView.vue` L16–32 | #10 帮助 | server_path 未设只给引导卡"去设置填 PalServer 根目录"，无排错/定位帮助 | 新手第一道坎无深层引导，可能卡死在"看不到任何世界" |

> 说明：**A1–A6 为代码走查即可确证的设计/逻辑问题**（无需用户测试）；**A7–A8 及 §1.4 卡点为需用户实测验证的假设**。

## 1.4 认知走查（核心任务：本地单机 → 专用服整包迁移）

走查问题框架：*用户能否从当前界面状态，明确知道下一步做什么？*

| 步骤 | 用户目标 | 界面是否给出明确行动 | 心智模型匹配度 | 卡点判定 |
|------|---------|---------------------|--------------|---------|
| 首次打开 | 看到我的世界 | 需先设 server_path（引导卡） | 弱：用户不知 PalServer 在哪 | **卡**（A8 假设） |
| 发现世界 | 确认哪个是单机/哪个是服 | 卡片有来源标签（src-steam/src-server，L49/L79） | 强 | 通过 |
| 触发迁移 | 把单机搬到服 | 卡片"迁移"→跳页预选源 | 强（衔接好） | 通过 |
| 选目标 | 指定专用服世界 | 目标下拉只列服务器 | 强 | 通过 |
| 执行 | 确认并拷贝 | 二次确认弹窗 | 中：显示绝对路径/round-trip（A4/A6） | 勉强 |
| **验证** | **确认世界可玩** | **UI 无任何"启服验证"引导** | **断裂**：用户不知要做这步 | **强卡（B4 假设）** |
| 修复角色 | 进服变新角色后补救 | 顶部"① 修复主机存档 P0 灵魂步骤" | **误导**：鼓励提前做高风险操作 | **风险（A1）** |

**关键走查结论**：任务在"执行"之前流畅，但在**「验证世界可玩」闭环处断裂**，且**「修复主机存档」被错误地前置并拔高优先级**，与文档风险隔离原则相悖。

## 1.6 量化/定性研究设计方案（待老板拍板执行）

- **样本量**：定性 5–8 人（主题饱和）；定量 SUS ≥ 15 人（统计意义）。

## 2.2 研究目标与核心问题（RQ）

本研究服务一个战略决策：**本项目的"部署服务器 + 数据迁移"该走哪条产品路线**。具体拆为 5 个研究问题：

| 编号 | 研究问题 | 类型 | 对应决策 |
|------|---------|------|---------|
| **RQ1** | 目标用户在"把单机世界搬到专用服"时，真实的心智模型与痛点是什么？（是否预期"迁完就能玩、角色还在"） | 生成性 / 定性 | 验证 B 路（角色/公会迁移）是否为核心需求 |
| **RQ2** | 用户能否理解并接受"源=全部存档、目标=专用服世界"的约束？困惑点在哪？ | 评估性 / 定性+定量 | 确认/推翻当前下拉设计 |
| **RQ3** | 相比"自动发现世界"，用户是否更偏好"自己选源路径 + 自己选目标路径"的直接操作？两类用户的占比？ | 评估性 / 混合 | **直接回答你提的"识别 vs 手选"问题** |
| **RQ4** | 迁移流程的哪些步骤造成不信任/焦虑（覆盖前无备份提示、确认弹窗暴露原始 GUID、迁移后无"去验"引导）？ | 评估性 / 定性 | 驱动 A1–A6 修复优先级 |
| **RQ5** | 部署专用服本身（找 Steam 库、配置、启停）的主要障碍是什么？ | 生成性 / 定性 | 部署向导设计输入 |

> 注：RQ1–RQ5 与 Part 1 §1.1.1 的 RQ1–RQ5 是同一组研究问题，两份文档从不同角度（审计基线 vs 研究计划）切入。Part 1 侧重"界面走查发现的问题"，Part 2 侧重"如何用科学研究验证这些问题并指导产品决策"。

## 2.3 研究方法论：混合方法 + 三角验证

采用 **解释性序列混合设计（exploratory sequential mixed methods）**：先用定性挖"为什么"，再用定量验证"多普遍"。三阶段：

### 阶段一 · 生成性研究（Generative Research）
- **方法**：半结构化深度访谈（45–60 min）+ 情境调查（contextual inquiry，观察用户实际找存档目录的过程）。
- **目的**：建立用户画像、痛点地图、心智模型（RQ1、RQ5）。
- **样本**：6–8 人（见 §2.4 细分），覆盖新手到进阶。
- **产出**：亲和图（affinity mapping）、痛点主题、用户旅程（当前手动做法 vs 期望）。

### 阶段二 · 可用性测试（Usability Testing）
- **方法**：任务场景 + 出声思考（think-aloud），在**真实环境**（用户自己的机器装好项目）执行。
- **任务卡**（草案）：
  1. 找到你电脑上的一个单机世界和一个专用服世界。
  2. 把单机世界迁移到专用服。
  3. 进入游戏，确认世界可玩、角色在不在。
  4. （进阶）角色变成了新角色，你期望工具怎么帮你？
- **度量**：任务完成率、时长、错误数、SEQ（Single Ease Question，1–7）、定性观察（困惑/焦虑时刻）。
- **样本**：8–10 人。
- **产出**：可用性问题清单、SEQ 均值、认知走查补充。

### 阶段三 · 定量问卷（Survey）
- **方法**：在线问卷，SUS（System Usability Scale，10 题，0–100）+ SEQ + 目标偏好选择题（RQ3 直接量化）。
- **样本**：≥ 30 人（达到 SUS 信度下限）。
- **目的**：把阶段一/二的定性发现量化、外推。

### 三角验证
定性访谈 + 可用性测试 + 问卷三源交叉，只有**至少两源一致**的发现才升级为"确证"，否则保留为"待观察"。

## 2.6 竞品基准分析（确证级 · 真实代码证据）

### 2.6.1 研究对象：PalworldSaveTools（PST，deafdudecomputers）
- 技术栈：Python + PySide6 桌面应用，直接读写压缩 SAV/GVAS。
- 定位：**全能存档编辑瑞士军刀**（编辑帕鲁/玩家/公会/地图 + 转换 + 迁移）。

### 2.6.2 它的"迁移"到底怎么设计的（读源码确认）

| 维度 | PST 的做法（源码证据） |
|------|----------------------|
| **世界发现** | **无自动发现**。用户点 Browse，用 `QFileDialog` 自己选 `Level.sav`（`fix_host_save.py:424` `choose_level_file`）。 |
| **源/目标选择** | 选一个 `Level.sav` → 解析出玩家列表（UID/名/公会/等级）→ 在左右两棵树里**各选一个 GUID**做交换。 |
| **"世界迁移"** | **不是文件拷贝功能**。README "Host → Server Transfer" 指南写的是：用户**自己手动复制粘贴** `Level.sav`+`Players` 文件夹进专用服目录，再用 Fix Host Save 修 GUID（L340–345）。工具只做 GUID 改写。 |
| **核心能力** | **深度 GVAS 改写**：`fix_host_save.py` 的 `fix_save` 真正解压→改 `PlayerUId`/`InstanceId`/`Guild`/`OwnerPlayerUId`/`PalStorageContainerId`→重压。这才是它"迁移"的价值。 |
| **角色/公会** | 与"世界拷贝"解耦，作为独立工具（Character Transfer / Fix Host Save），且**默认就在产品里、不隐藏**。 |
| **风险提示** | 每次操作前 `backup_whole_directory`（L440），并有 `warning.world_id` 橙色警告文案。 |

### 2.6.3 本项目当前设计（读设计稿 + 审计确认）

| 维度 | 本项目的做法 |
|------|------------|
| **世界发现** | **自动发现**为唯一入口：`SaveManagementView` 自动扫 Steam/AppData + 专用服 `SaveGames`，手动选目录为兜底（设计稿 Part 1 §1.2）。 |
| **源/目标选择** | 源下拉=全部存档，目标下拉=专用服世界（已确认正确，见审计纠正 Part 1 §1.2.1）。 |
| **"世界迁移"** | **文件级整包拷贝**：`migrate_world_to_server` 定位含 `Level.sav` 的数据层→整包复制，不解析/不改写 `.sav` 内部。 |
| **核心能力** | 安全的世界文件搬运 + 覆盖前备份 + 去重 + 回滚。 |
| **角色/公会** | **显式延后**到"B 路 / Fix Host"，且设计稿 §1.7 要求"世界验证前不得触发"——在 UI 上被折叠/后置。 |
| **风险提示** | 部分（停服限制、备份）有，但确认弹窗暴露原始 GUID、迁移后无"去验"引导（审计 A4/A6）。 |

### 2.6.4 关键差异与设计启示（确证级）

1. **PST 的"手选路径"不是因为它更优，而是因为它的价值在"改写"——改写必须进文件，所以顺手让用户指路径。** 它的"迁移"体验其实更原始（手动复制粘贴文件）。
2. **PST 把 GUID 改写作为一等公民**；我们把它当"下一个阶段"。这直接导致你感到"迁移没完成"——**世界拷过去了，但角色变新人，体验断层**。对用户的真实心智（RQ1 假设 H1），"成功迁移"= "进去还能玩、还是我"；只拷文件不算完。
3. **我们的自动发现是差异化优势**（对 S1 小白服主极有价值），不应为迎合"像同行"而删掉。但**手动路径选择不应被移除**——S3 技术玩家和"F:\1 这类手动备份"场景需要它（设计稿 §1.2 本就保留手动兜底，迁移页移除它是一步退让）。

## 2.7 初步发现（当前"结果"）

### 2.7.1 确证级（无需用户研究即可成立）
- **F1**：当前源/目标下拉设计（源=全部、目标=专用服）**正确**，不是缺陷（已与设计稿、审计对齐）。
- **F2**：同行 PST 采用"手动选 `Level.sav` + GUID 改写"模型，且其"世界迁移"实为手动文件复制；它**没有**自动发现、也**没有**整包拷贝功能。
- **F3**：本项目相对 PST 的核心差异是"自动发现 + 安全整包拷贝"，但**缺少 PST 已具备的 GUID/角色改写能力**，造成"世界可搬、角色断裂"的体验缺口。

### 2.7.2 待验假设（必须经研究确认，禁止当结论报）
- **H1（RQ1）**：多数用户认为"迁移成功"应包含"角色可玩、身份保留"，而非仅文件到位。
- **H2（RQ2）**：新手对"目标只有专用服"的困惑，可通过一行引导文案消除，而非需要改交互结构。
- **H3（RQ3）**：用户偏好呈**分段**——S1 强烈偏好自动发现，S3 强烈偏好手选路径；混合模型（自动发现默认 + 手选常驻兜底）满意度最高。
- **H4（RQ4）**：迁移后"无启服验证引导"与"确认弹窗暴露 GUID"是 Top 焦虑源。
- **H5（RQ5）**：部署专用服的最大障碍是"找不到 Steam 库 / 不会配"而非"不会迁移"。

## 2.8 数据分析计划

- **定性**（阶段一/二）：Braun & Clarke 主题分析法（thematic analysis），6 步；用亲和图聚合；研究员 + 1 名协作者独立编码后比对（inter-coder reliability）。
- **定量**（阶段三）：SUS 按 Brooke(1996) 标准计分（反向题反转、×2.5）；SEQ 取均值；目标偏好做卡方/占比检验；细分 S1/S2/S3 分组对比。
- **合成**：用 §2.3 三角验证规则升级发现等级；输出"设计决策矩阵"（见 §2.10）。

## 2.10 设计建议（基于确证证据 + 待研究确认的方向）

> 以下为**研究员基于现有确证证据（F1–F3）的初步方向**；带 * 的项需研究数据最终确认。

### 2.10.1 直接回答核心问题：自动识别 vs 手动选路径
**建议：保留自动发现为默认，但恢复手动选路径为常驻一等能力——即混合模型，不是二选一。**
- 理由（确证）：自动发现是相对 PST 的差异化优势（F3），对 S1 小白服主降低致命错误（选错 `Level.sav`、拷进错误目录）；PST 的纯手选模型建立在其"改写"价值上，我们目前没有该价值，更不应放弃引导。
- 但设计稿 Part 1 §1.2 说"数据迁移页不再有手动选本地目录"——这步**过度了**。应保留手动选路径作为兜底（尤其适配 F:\1 这类用户自有备份目录），与自动发现并列，而非移除。*（H3 将量化两类用户占比以定默认焦点）*

### 2.10.2 迁移"完整性"缺口（最关键）
**建议：把"角色/公会可玩"从"下一阶段"提升为迁移闭环的必要一环，至少提供显式、可达的 Fix Host 入口。**
- 理由（确证 + 你的原话）：你亲测"世界可玩但角色不在"，且设计稿把 GUID 改写折叠后置——这与用户对"成功迁移"的心智（H1）冲突，是体验断层的根因。PST 正是把 Fix Host 作为一等公民才被接受为"迁移工具"。
- *H1 量化后将决定：是默认在迁移后自动引导 Fix Host，还是仅提供入口。*

### 2.10.3 信任与焦虑（驱动 A1–A6 优先级）
- 立即可做（确证，不依赖研究）：A4 确认弹窗去 GUID、A6 迁移后加"启服验证"引导、A1 把高风险操作正确隔离（已排期）。
- *H4 将验证这些是否真是 Top 焦虑，以及是否还需补充"覆盖前差异预览"。*

### 2.10.4 部署服务器
- *H5 假设部署障碍在"找库/配置"而非"迁移"。建议研究后做轻量部署向导（探测 Steam 库 + 一键填 `server_path`），与迁移体验解耦。*
