# PRD：本地单机存档 → 专用服务器存档 迁移

> 项目：Palworld-Server-Manager（Tauri2 + Vue3 + TypeScript 桌面应用）
> 文档类型：简单版 PRD（产品目标 + 用户故事 + 需求池 + UI 设计提示 + 待确认问题）
> 日期：2026-07-25
> 作者：产品经理 许清楚（Xu）

---

## 1. 项目信息

- **Language（文档语言）**：简体中文
- **Programming Language（技术栈）**：Tauri2 + Vue3 + TypeScript（桌面应用，**非** Vite + React 默认栈；本项为用户指定栈）
- **Project Name（snake_case）**：`local_singleplayer_to_server_migration`
- **原始需求复述**：
  用户需要把本地单机世界（含玩家角色与公会/领地归属）迁移到 Palworld 专用服务器，使玩家能以**原有角色**登入、且**原有公会与领地归属保持不变**。迁移必须采用 PalworldSaveTools 风格的「深度存档改写」语义（GUID / 角色 / 公会重映射），**而非整文件夹拷贝**。应用需提供备份、回滚与安全引导，防止出现历史上「新角色 + 领地无主」的错误结果。

---

## 2. 核心定义与前提（防止迁移错误 —— 必须锁定）

### 2.1 「迁移」的准确定义
将本地单机世界的 **「世界数据 + 玩家角色 + 公会/领地归属」** 整体转移到专用服务器，使玩家能以**原有角色**登入、且**原有公会与领地归属保持不变**。

### 2.2 明确反对
- **仅整包拷贝世界文件夹**（如历史上把 `1D5D1F30` 整包拷到 `SaveGames/0/`）：服务器能加载，但玩家登入为**新建角色**、**领地无主人**——因为单机角色 UID（`0000...0001`）与公会归属未被重映射到服务器玩家身份。

### 2.3 明确必须包含
1. 世界文件转移（`Level.sav` 及 9 个 Map、`Players/<UID>.sav`、`<UID>_dps.sav` 等）。
2. 角色 / 公会 GUID 与归属重映射（**Fix Host 风格**：GUID 双向字节交换 + `_dps` 结构化改写 + 文件名交换 + 公会 RawData 内旧 UID hex 显式替换）。

### 2.4 事实基线（真实路径，已纠正）
- **本地单机存档（唯一真·世界）**：
  `C:\Users\pengq\AppData\Local\Pal\Saved\SaveGames\76561199381352956\1D5D1F304D3AA1FE2818BA98D5223DFE\`
  - 含 `Level.sav`（525,718 B）、`Players/00000000000000000000000000000001.sav`（单机管理员）、`LevelMeta.sav`、`LocalData.sav`、`WorldOption.sav`、`backup/`。
  - ⚠️ 同目录下 3 个 GUID 文件夹（`1A91A615` / `353D806B` / `EFD77CBB`）**只是客户端 `LocalData.sav` 残桩，不是世界**，迁移时**严禁**当世界处理。
- **专用服务器存档**：
  `E:\SteamLibrary\steamapps\common\PalServer\Pal\Saved\SaveGames\0\`
  - 含 `1A91A615...`（用户当前 live 世界）、`1D5D1F30...`（当前为 7/24 的一份**整包拷贝错误示范**，567,557 B）。

### 2.5 安全约束
- 迁移**前**必须对目标服务器世界做**完整备份**。
- 迁移**后**必须能**一键回滚**到备份。
- 步骤顺序：**先验证世界可玩（仅世界文件），再处理角色/公会改写**。不得诱导用户在验证世界前执行高风险 GUID 改写。

## 3. 产品目标（Product Goals）

- **G1（正确性）**：迁移后玩家以原有角色登入，公会与领地归属完整保留——闭环必须覆盖三类引用：「角色 UID + 公会 GUID + 公会 RawData 内旧 UID 字符串」。
- **G2（安全性）**：迁移全程可备份、可回滚、可验证，绝不允许因误操作导致服务器世界损坏或领地无主。
- **G3（易用性 / 防误操作）**：以清晰引导将「整包拷贝」与「深度迁移」明确区分，从 UX 上降低用户误选整包拷贝导致失败的概率。

---

## 4. 用户故事（User Stories）

- **US1**：作为一名想把单机进度搬到服务器的玩家，我希望应用自动发现我的单机世界与服务器世界并提示两者差异，以便我准确确认迁移来源与目标。
- **US2**：作为一名执行迁移的用户，我希望应用先帮我备份目标服务器世界并验证「世界文件可加载/可玩」，以便我在确认基础正确后再做高风险改写。
- **US3**：作为一名执行迁移的用户，我希望应用按 Fix Host 逻辑重映射我的角色 UID、公会 GUID 与领地归属，以便登入后是原有角色且领地有主人。
- **US4**：作为一名谨慎的用户，我希望迁移失败时一键回滚到备份，以便我不会丢失服务器原有世界。
- **US5**：作为一名潜在的多玩家存档用户，我希望应用能正确处理「单机含多个玩家角色」的情况（或明确提示暂不支持），以便我不会误迁移导致数据错乱。

## 5. 需求池（Requirements Pool）

### P0（Must have）
- **P0-1 正确的迁移语义与闭环**：实现「世界文件转移 + 角色/公会 GUID 与归属重映射（Fix Host 风格）」的完整迁移闭环，**明确区别于整包拷贝**。
- **P0-2 重映射硬缺口补齐**：在含旧 UID 的公会 RawData 中，将旧玩家 UID 的 32 位 hex 显式替换为新 UID 的 32 位 hex（补齐 `group_name` 等非 16 字节 GUID 字符串引用，对应 `fix_host.rs` 已知缺口）。
- **P0-3 迁移前备份**：对目标服务器世界文件夹执行带时间戳的完整备份，备份可独立还原。
- **P0-4 迁移后回滚**：提供一键回滚到备份的能力，回滚后服务器世界恢复到迁移前状态。
- **P0-5 源/目标识别正确性**：自动识别并**仅处理**「真·单机世界」文件夹，严格排除同目录下的 `LocalData.sav` 残桩 GUID 文件夹（`1A91A615` / `353D806B` / `EFD77CBB`）。

### P1（Should have）
- **P1-1 验证引导顺序**：强制「先验证世界文件可加载/可玩 → 再执行角色/公会改写」的流程；UI 未通过世界验证前**禁用**高风险改写按钮。
- **P1-2 防误操作系统确认**：执行高风险 GUID 改写前弹出明确警示（说明「仅整包拷贝会导致新角色 + 领地无主」），需用户二次确认。
- **P1-3 迁移结果校验**：迁移完成后校验领地归属链（基地点位 `group_id_belong_to` → `BaseCampSaveData.group_id` → `GroupSaveDataMap.base_ids[]` ↔ `admin_player_uid`），并给出「成功 / 异常」报告。
- **P1-4 代码质量门槛**：`fix_host.rs` 与 `sav_io.rs`（GameVersion GVAS 流须用 `Default` 而非 `Palworld`）改动必须通过 `cargo test` 验证并 git 提交后，方可纳入发布。

### P2（Nice to have）
- **P2-1 源/目标清晰区分的 UX 文案**：界面用标签明确「本地单机世界（源）」与「专用服务器世界（目标）」，并展示路径与文件清单。
- **P2-2 多玩家存档支持或明确提示**：对含多个 `Players/<UID>.sav` 的存档，支持映射或明确提示「暂仅支持单机管理员角色迁移」。
- **P2-3 迁移日志与可导出报告**：记录备份路径、改写项、校验结果，支持导出迁移报告。

## 6. UI 设计提示（UI Design Draft）

- **整体布局**：迁移向导式（Stepper）界面，至少 3 步：
  ① 选择源（单机世界）/ 目标（服务器世界） → ② 备份与验证世界 → ③ 角色/公会重映射与执行 → 完成报告。
- **源/目标面板**：左右双栏分别展示「本地单机世界（源）」与「专用服务器世界（目标）」的路径、文件清单、识别状态（如「✓ 真·世界」/「⚠ 残桩文件夹已忽略」）。
- **风险提示区**：在重映射步骤前显示醒目警示卡片，说明「仅整包拷贝会导致新角色 + 领地无主」，并提供「了解正确迁移方式」说明入口。
- **按钮状态**：未通过「世界验证」前，「执行重映射 / 高风险改写」按钮**置灰禁用**；「创建备份」「验证世界」按钮优先可用。
- **结果页**：展示备份路径、改写项清单、归属链校验结果（公会 / 会长 / 领地数量），并提供「一键回滚」入口。

## 7. 待确认问题（Open Questions —— 需用户拍板）

1. **管理员角色映射目标**：单机 `00000000000000000000000000000001` 管理员角色，应映射到服务器上的哪个玩家 UID？（映射到服务器首个登入玩家？还是预先指定的某个 Steam UID？）
2. **多玩家存档处理**：若单机存档含多个 `Players/<UID>.sav`，本次是否支持批量映射？还是仅迁移管理员角色并提示其余需手动处理？
3. **Fix Host 改写执行方式**：重映射是否做成 App 内「一键执行」；还是保留手动调用（脚本 / CLI）？若一键执行，是否需内置 `cargo test` 通过后的产物？
4. **新 UID 来源**：服务器侧新玩家 UID 如何确定（登录时由服务器分配 vs 迁移时预置）？直接影响 `fix_host.rs` 新旧 UID 参数传入方式。
5. **目标世界冲突策略**：目标 `SaveGames/0/` 下已存在 `1A91A615`（live 世界）与 `1D5D1F30`（错误拷贝），迁移产物放新 GUID 还是覆盖？是否先清理错误拷贝？
6. **回滚粒度**：回滚是仅恢复世界文件，还是连同角色/公会改写一并回退到备份快照？
