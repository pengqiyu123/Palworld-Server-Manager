# Palworld 迁移与备份 V4 实施记录

**日期**：2026-07-27
**状态**：代码、自动化测试、真实存档副本测试、界面与安装器验证完成；V4 最终进服验收待用户执行。

## 交付范围

V4 将世界、角色和公会拆成可恢复的独立步骤：

1. 迁移整个世界，并先完整备份目标服务器世界。
2. 用户进服创建目标角色后，转移完整角色数据，同时保留目标 UID、InstanceId、GroupId、容器身份和现有公会关系。
3. 仅在整世界迁移工作流中可选恢复原公会；朋友角色导入不具备公会恢复能力。
4. 用户进服确认后完成工作流，或从迁移前完整备份回滚。

工作流写入 `backups/_system/workflows/`，应用重启只恢复显示状态，不自动继续写存档。所有写操作先检查服务器已停止，并通过暂存、回读解析、同目录替换及失败恢复完成。

## 备份结构

默认目录为开发项目的 `Palworld/backups`，发布后为管理器 exe 旁的 `backups`。自定义位置只在用户明确选择后生效，失败时不回退到 LocalAppData。

```text
backups/
  local/       # 手动创建的本机世界完整备份
  server/      # 服务器世界完整备份
  snapshots/   # 危险操作前的轻量回滚点
  _system/     # 工作流与索引，不在 UI 展示
```

每份备份含独立 `manifest.json` 和 SHA-256 清单。完整备份只允许手动删除；每个世界保留最近 3 个已完成操作回滚点，写入中、恢复失败和需人工处理的记录不自动清理。自定义位置变更后，历史根仍参与列表与恢复。

## 关键正确性结论

- 完整角色转移先删除目标 UID 的旧 CSPM 玩家记录，再插入映射到目标身份的源记录，提交后目标 UID 恰好一条玩家记录。
- 角色转移不修改公会成员、管理员、据点和权限数据，任一子数据失败时不提交部分结果。
- 原公会恢复只读取后端工作流记录的原主角色与原公会；目标已加入其他公会时拒绝执行，仅在原主角色原本是管理员时恢复管理员身份。
- 当前版本兼容玩家文件缺少 `GroupId`、动态物品数组形式及 Palworld 四个 `u32` 的 GUID 文本格式。
- 启动时检测中断工作流并恢复未完成写入；故障注入覆盖新增文件删除和旧文件还原。

## 最终人工验收

使用实际服务器前再次确认服务器已停止并保留 `F:\1` 外部备份。按“世界迁移 -> 创建服务器角色 -> 完整角色转移 -> 可选恢复原公会”的顺序执行。进服检查背包、装备、帕鲁、公会、据点和权限；正常退出触发保存后，再次启动并复查。只有完成这一步后，V4 才能标记为实机最终验收通过。

## 可复用经验

1. 世界复制、角色数据转移和公会归属是三个不同事务，应独立提交、独立回滚。
2. 角色迁移必须保留目标登录身份并对 CSPM 去重，不能依赖随机 GUID 或全局字节替换。
3. 完整备份保护迁移基线，轻量回滚点保护单步操作；两者不能互相替代。
4. 真实存档副本和游戏再次保存是格式正确性的最终证据，纯解析成功不足以证明引用关系安全。
5. 前端进度必须来自真实后端阶段；游戏内验证必须由用户明确确认，不能自动宣称成功。
